# Home Hub — Design Document

**Date:** 2026-10-06
**Status:** Approved design, pending implementation plan
**Deployment target:** Docker container inside an LXC on the user's Proxmox server

## 1. Summary

A self-hosted "Home Hub" web application with an integrated Telegram bot. Phase 1 delivers a home medicine tracker: add medicines by photographing the package, AI extraction of name/dosage/expiry/purpose via z.ai, expiry and opened-after tracking, quantity/low-stock tracking, dose logging through casual Telegram messages, and Telegram notifications. Phases 2 and 3 add a shared family shopping list and a shared family task tracker on the same infrastructure.

Language support: Polish, Russian, Ukrainian, English (UI switcher; medicine descriptions generated in all four languages).

## 2. Architecture

One Docker container (`docker compose up`) containing:

- **Web app:** Python 3.12 / FastAPI, server-rendered pages with light JS for camera capture. Mobile-first UI; installable to the phone home screen.
- **Database:** SQLite (single file, WAL mode).
- **Telegram bot:** aiogram, long-polling (no inbound ports required).
- **Scheduler:** APScheduler, daily check at a configurable hour (default 9:00).
- **AI integration:** z.ai OpenAI-compatible API. Two uses: (a) vision extraction from package photos, (b) interpretation of casual Telegram text messages. Model name, API base URL, and API key are config values so the provider can be swapped later.

All state (SQLite file + uploaded photos) lives in one Docker volume. Backing up = copying that volume.

## 3. Phase 1 — Medicine tracker

### 3.1 Data model

`medicine` table:

| Field | Notes |
|---|---|
| name | e.g. "Paracetamol 500 mg" |
| active_ingredient | optional |
| form | tablets / syrup / drops / ointment / other |
| dosage_pl / dosage_ru / dosage_uk / dosage_en | how to take it (e.g. "1 tablet 2× daily"), generated by AI in all four languages |
| description_pl / description_ru / description_uk / description_en | short "what it is for", generated by AI in all four languages |
| expiry_date | may be null if unknown |
| opened_at | null until first use |
| discard_after_days | days usable after opening (e.g. 30 for syrup); null = not applicable |
| quantity + unit | e.g. 23 tablets, or 2 packages |
| low_stock_threshold | default 3 |
| photo_path | nullable |
| created_at / updated_at | |

Dose-taking events are appended to an `events` table (medicine_id, timestamp, actor, delta, note) — this also provides the "who did what" history used by Phases 2–3.

### 3.2 Adding a medicine (main flow)

1. Web app → "Add" → phone camera opens (HTML `getUserMedia`; file-picker fallback) → up to 2 photos (front + expiry side).
2. Backend sends photos to z.ai vision → expects structured JSON back: name, active ingredient, form, dosage (×4 languages), expiry date(s), purpose (×4 languages). Prompt requests all four language strings in one call.
3. Pre-filled, fully editable form is shown. Nothing is saved until the user confirms. Manual entry is always available and never blocked by AI availability.
4. **Expiry date is required.** If the AI could not read an expiry date from the photo, the form highlights the expiry field as "enter manually" and will not save until the user types it.
5. On save: row inserted, photo stored in the volume.

**Multiple packages in one photo:** if the AI detects more than one medicine box in the photo, it does NOT guess. The app asks the user to photograph each box separately, or to photograph the barcode (the barcode photo replaces the front photo as the identification source and the flow restarts from step 2).

**AI failure handling:** if z.ai is unreachable or returns unusable output, the app opens an empty form (expiry still required), marks the item with status `needs_ai_data`, and a background job retries extraction periodically (with backoff, e.g. hourly) using the stored photo. The user can also trigger "re-read photo" manually from the item page. The photo is always kept.

### 3.3 Notifications (daily check + immediate)

| Condition | When | Message includes |
|---|---|---|
| Expiry | 7 days before expiry date, and on the expiry day | name, date, buttons: [Discarded ✓] [Snooze 1 month] |
| Opened-after | 1 day before discard date, and on the discard day | name, "opened on X", buttons: [Discarded ✓] [Snooze 1 week] |
| Low stock | quantity reaches threshold (default 3), and again when taking the last dose | name, quantity left, button: [Add to shopping list] (Phase 2 hook; until then a no-op/log) |

Rules:

- Medicine alerts go only to the admin (the user).
- Snoozed alerts re-fire after the snooze period. Snooze state is persisted.
- Only medicines with a known date are tracked; items with `null` expiry are listed in the web UI under "no date set" so gaps are visible.

### 3.4 Telegram bot

Two roles:

**Notifications** — as above, delivered to the admin's chat.

**Conversational commands** (free text, language-agnostic — interpreted by the text AI):

- "took 1 paracetamol" / "wziąłem paracetamol" → matches medicine (fuzzy + AI-assisted), decrements quantity, appends event, replies with remaining quantity. Ambiguity → inline buttons to pick the exact medicine; the bot never guesses.
- "opened aspirin" → sets `opened_at` to now, confirms.
- "how much paracetamol left?" → replies.
- "expired soon?" → lists medicines expiring within 7 days.
- "I have a headache, do I have something for it?" (any language) → symptom query: the text AI matches the symptom against the stored purpose descriptions and active ingredients, and replies with matching medicines from the cabinet — including their remaining quantity and whether they're still usable (not expired, and not past the discard-after-opening date). If nothing matches, it says so rather than suggesting anything not owned.

Web app remains the source of truth; everything the bot changes is visible and editable there.

### 3.5 Family members (Telegram identity, no web accounts)

- Family members are Telegram user IDs approved once by the admin ("who are you" prompt on first message → admin approves).
- Approved members can use dose logging and queries; they do **not** receive medicine alerts (admin only).
- This identity system is the foundation for Phases 2–3 (shared lists, attribution).

## 4. Phase 2 — Shared shopping list (second delivery)

- One shared list for the whole family (no per-person lists).
- Add via web UI or Telegram ("add milk and bread" → itemized). Each item records who added it and when; check-offs record who bought it.
- Low-stock notification button "Add to shopping list" becomes live.
- History view per item / short recent-activity feed.

## 5. Phase 3 — Shared family task tracker (third delivery)

- One shared task list; tasks have title, optional due date, optional assignee (a Telegram-identified member).
- Reminders for due dates through the bot; tasks assigned to a member are also mentioned to that member.
- Same attribution/history model as the shopping list.

## 6. i18n

- UI languages: PL, RU, UK, EN — switchable in the web app; the bot replies in the language of the sender's chosen preference. **Default bot language is Polish**; new users start with Polish and can switch ("language ru" command or button).
- Medicine descriptions are generated and stored in all four languages simultaneously (single AI call returns all four).

## 7. Security & networking

- Web app is reachable only via the user's VPN / LAN; not exposed to the internet.
- Optional single admin password (config-gated; default off since access is VPN-protected).
- Telegram: long-polling outbound only; bot responds exclusively to approved Telegram user IDs; z.ai API key and bot token stored in an `.env` file outside the web root.

## 8. Backups

Automatic nightly backup inside the container: copy the SQLite file (using SQLite's backup API for consistency) + photos to a `backups/` folder in the volume, keep last N (default 14) days. Documented one-command restore. Optionally the folder can be a second mount pointing at a Proxmox host path or NAS.

## 9. Error handling summary

| Failure | Behavior |
|---|---|
| z.ai unreachable / bad output | Empty editable form; item flagged `needs_ai_data`; background retry with backoff; manual "re-read photo" button |
| No expiry on package | Stored as null; shown in "no date set" list |
| Telegram send failure | Retry with backoff; web app unaffected (data is local) |
| Ambiguous bot command | Inline-button clarification; never guess |
| DB corruption | Restore from nightly backup (documented) |

## 10. Testing

- Unit tests: date logic (expiry/opened/low-stock evaluation), quantity arithmetic, i18n rendering.
- Integration tests: add-medicine flow with a mocked z.ai endpoint (including failure → retry path); notification scheduler against a seeded DB; bot command parsing with recorded example messages in all four languages.
- Manual smoke test on the phone: camera capture → confirm form → save → Telegram notification.

## 11. Out of scope

- Multi-user web accounts (Telegram identity is used instead).
- Barcode scanning (photos only; can be a future addition).
- Public internet exposure of the web app.
